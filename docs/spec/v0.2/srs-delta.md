本文件只登记相对 [v0.1 SRS](../srs.md) 的增量。未列出的 REQ-01、REQ-04、REQ-05、REQ-10 继续按 v0.1 执行；本文件不复制其原文。

| **REQ-11** | 计划身份与 family | 每个 round 对应一个 child job；campaign 是 family 下的特殊 child，不是 round；fixed 模式 = 一个 family + 一个 `round_no=1` 的 round。`jobs` 增加 `family_id`、`job_kind`、`parent_job_id`、`round_no` 与 | **REQ-12** | 探索信封与自动准入 | 人批准的是一份探索信封加首份计划（campaign 计划或 fixed round 1 计划），而不是逐轮批准计划。信封字段固定为 `mode`（`fixed`/`guided`）、`allowed_mutation_families`、`mutation_limits`（`allowed_ops` + `max_input_bytes`）、`seed_corpus_digest`、`fuzz_image_digest`、`harness_digest`、`max_rounds`、`max_total_seconds`、`max_fuzz_seconds`、`accepted_signature_set` 与 `admission_predicate_version`；fixed 模式仍冻结退化信封，`envelope_digest` 非空；fixed 的 `allowed_mutation_families=[]`、`mutation_limits={"allowed_ops":[],"max_input_bytes":0}`、`max_fuzz_seconds=0`、`seed_corpus_digest=null`、`fuzz_image_digest=null`，`harness_digest` 与 `accepted_signature_set` 仍必填；guided 的 `fuzz_image_digest` 默认等于固定工具链镜像摘要。轮次内由确定性 policy 自动准入；准入写入独立 `admissions` 表，记录 `approval_kind=policy`、`envelope_digest`、`parent_approval_digest`、`seed_digest` 与 `decided_at`，并追加审计事件 `round_admitted`。policy 准入不得写 `reviews`；`reviews` 只保存人的批准或拒绝。人批后生成 `family_approvals` 行，`approval_digest` 由 `{family_id, envelope_digest, first_plan_digest, reviewer_id, decided_at}` 计算并排除自身；换信封产生新 approval 并以 `supersedes` 指向旧 approval（只追加 `family_approvals`，不重写 `reviews`），旧轮次保留旧摘要。`mutation_limits` 进入 `envelope_digest`，`max_rounds` 由 predicate 检查。 | 信封覆盖范围内的下一轮无需等待人工审核即可准入；超出 `max_rounds`、`max_total_seconds`、`max_fuzz_seconds`、`allowed_mutation_families`、`mutation_limits` 或 `accepted_signature_set` 的轮次被拒绝并给出原因码；首份计划 `parent_approval_digest=null` 可被审核并在后续轮次引用非空摘要；换信封后旧 approval 被 `supersedes`，旧轮次摘要不变；`admissions` 行数与 `round_admitted` 事件一一对应；查询 `reviews` 不出现 policy 记录。 |
| **REQ-13** | 假设到实验 | 模型只产 hypothesis，不产事实、判定，不直接调用工具，不合成可执行 fuzz harness。v0.2 `AgentOutput` 覆盖 v0.1 的 `fact` 与 `hypothesis` 两种 kind：模型来源 finding 只允许 `kind=hypothesis`；确定性工具事实改走 `ToolResult` 与证据引用，不由模型 `fact` 转述；v1 `AgentOutput` 只读兼容。每条可执行假设必须落成 `ExperimentSpec`，字段为 `target_symbol`、`target_path`、`target_line`、`input_family`、`mutation_constraints`、`expected_signature`、`rationale`、`evidence_refs` 与 `confidence`。`expected_signature` 与 plan `asan_signature`、信封签名项同结构：`error`/`function`/`source` 必填，`operation`/`access_size` 可选，匹配时全字段严格相等。`input_family` 与 `mutation_constraints` 必须逐项落在信封内，`evidence_refs` 必须可解析；规范化摘要进入 plan 的 `experiment_digest`。实验由确定性规划器生成并受准入检查；删除或修改 hypothesis 不得改变由同一组回放观测得出的判定。B04-H 报告 hypothesis 质量，不能替换 v0.1 的 B04-A。 | 信封外的 ExperimentSpec 在准入前被拒绝；mutation 操作或字节上限超出信封时被拒绝；`operation`/`access_size` 不同或可选字段缺失/存在不一致时不算匹配；没有可解析 `evidence_refs` 的假设不能生成实验；模型输出 `kind=fact` 被阻断且确定性事实不经模型出口；把 hypothesis 文本替换或删除后，六次回放的判定结果不变；模型输出不能触发未登记工具调用。 |
| **REQ-14** | family 预算账本 | 预算以 family 级原子行记账，按唯一执行协议落地（见[接口契约增量](interface-contract-delta.md)第 7 节）：启动容器前先校验总余额与（fuzz 时的）`min(remaining_total_seconds, remaining_fuzz_seconds) >= 1` 并下发为容器硬超时上限；容器退出后在独立短事务内执行原子条件 `UPDATE ... WHERE remaining >= x` 并写 `budget_charges`，禁止先读后写的应用层扣减。`budget_charges` 记录 `family_id`、`job_id`、`step_key`、`attempt_no`、`charge_kind`、`seconds` 与 `fuzz_seconds`，幂等键为 `(job_id, step_key, attempt_no)`：恢复同一 attempt 不重复扣费，重试新 attempt 新扣费。`0 <= fuzz_seconds <= seconds`；fuzz 消耗同时扣总预算与 fuzz 子预算。`max_rounds` 由准入 predicate 检查 `round_no <= max_rounds`；`UNIQUE(parent_job_id, round_no)` 只防重复轮次。v0.2 保持单执行槽位，family 的 child 串行执行；数据库条件更新是对未来多 worker 的防御。`budget_ledger` 约束上下界与 `max_fuzz_seconds <= max_total_seconds`，禁止增加 `remaining_fuzz_seconds <= remaining_total_seconds` 的交叉 CHECK；DB 列 `remaining_total_seconds` 对应 JSON `remaining_seconds`；实际可执行 fuzz 上限为 `min(remaining_total_seconds, remaining_fuzz_seconds)`，任一不足即 `BUDGET_EXHAUSTED`；`charge_kind='fuzz'` 的 `fuzz_seconds >= 1` 与不足 1 秒向上取整规则不变。预算耗尽时进入终态并给出 `BUDGET_EXHAUSTED`。 | 并发扣减不会出现负余额（两个数据库连接模拟竞争，验证 SQL 原子性）；同一 `(job_id, step_key, attempt_no)` 恢复不会二次扣费，新 attempt 会再次扣费；轮次重复插入只成功一次；`round_no > max_rounds` 被 predicate 拒绝；耗尽后不可再建轮次；`general` 扣费后 `remaining_fuzz_seconds` 大于 `remaining_total_seconds` 不违反约束；fuzz 上限按 `min()` 判定；report 的预算 6 个字段可由 charge 按 family 重建。 |
| **REQ-15** | 构建溯源与可比性 | 构建输入使用结构化 `BuildSpec`，字段统一为 `kind`、`configure`（仅 cmake）、`build`、可选 `install`、`env`、`outputs`、`declared_compile_flags` 与 shell 专属 `shell_recipe_digest`/`shell_face_digest`/`shell_face_review`；Make 的 `CC` shim 统一放入 `env`。构建通过固定模板注入，不得自由拼接 shell。生效参数必须可核对：CMake 读 `compile_commands.json`，Make 读 `CC` shim 日志；shell 配方属于 legacy，`shell_recipe_digest` 只表示配方摘要，`shell_face_digest` 为预审基线核对面归一化摘要（构建阶段对实际日志走同一归一化比对），原文以 `build_provenance` 角色归档。多编译单元解析、封闭 7 项连写/分写归一化集合 `{-I, -L, -l, -D, -U, -isystem, -include}`、顺序保留与两版可比判据以[接口契约增量](interface-contract-delta.md)第 5 节为准：两版共同编译单元生效有序序列逐一严格相等且两版均满足“声明 ⊆ 生效（多重集包含）”，`-I a -I b` 与 `-I b -I a` 不相等；没有核对面时在冻结计划阶段失败并给出 `BUILD_PROVENANCE_MISSING`。工具链边界按固定镜像执行：已有 cmake、make、autoconf、automake 与 libFuzzer；缺少 pkg-config、libtool、ninja、git。 | 两版声明被生效覆盖且共同编译单元有序相等时计划可冻结；`-I a -I b` 与 `-I b -I a` 判为不相等；`build_provenance_rules_version` 写入 plan/report 并计入 `plan_digest`；`-I include` 与 `-Iinclude` 判为等价，`-I a -I b` 与 `-I b -I a` 判为不相等；CMake 与 Make 成功路径分别归档对应核对面原文；shell 配方无单独审核时不计为可比；没有核对面时冻结阶段失败；Oniguruma 类案例不要求新镜像。 |
